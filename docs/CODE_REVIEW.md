# WinVClip 代码审查报告（可维护性 / 架构）

审查对象：`winvclip` 仓库当前工作副本（HEAD = `4a29167`，工作区有未提交改动）。
审查方式：全仓结构与符号盘点 + 关键路径抽样精读（窗口过程、钩子、绘制、字形缓存、入口）+ 一次全量重编看编译器警告。

---

## 一、总评

**代码本身的质量明显高于同体量的个人 Win32 项目，坏消息全在"工程形态"上。**

写得好在哪（这些不要动）：

- `-Wall -Wextra` 全量重编 **0 警告**（`cmake --build build` 干净通过），说明类型/未用变量/隐式转换这些低级坑已经被守住了。
- 注释是**讲 why 而不讲 what**：`main.cpp:5196-5219` 解释钩子为什么只能接管窄范围、`main.cpp:5177-5180` 解释为什么不让面板拿焦点、`main.cpp:1175-1176` 解释 atlas 为什么不淘汰。这类注释是最贵的资产，重构时必须原样搬走。
- 资源生命周期在退出路径上是成对的（`main.cpp:5566-5586`：先停 worker 再释放 atlas/字体/D2D，顺序有明确理由）。
- 已经有 33 个能真跑的行为回归脚本（`test_noactivate.py`、`test_hook_passthrough.py`、`test_longpress.py` 这些是硬核回归，价值远超一般的"单元测试"）。

改不动在哪（本报告要解决的）：

| 维度 | 现状 | 风险 |
|---|---|---|
| 单文件规模 | `src/main.cpp` 5588 行 / 76 个顶层函数 / 38 个分节 | 任何改动都要在 2400 行上下文里定位；重编一次全量 |
| 全局可变状态 | 117 个 `g_*` 全局（`main.cpp:147-276` 起） | 不变式（`g_sel`/`g_top`/`g_view` 三者关系）靠调用方自觉维护 |
| 巨型函数 | `PanelProc` 491 行 / 25 个 case / 36 处 `PtIn`（`main.cpp:4071-4561`） | 加一个控件＝在 491 行里插一段，冲突与回归面最大 |
| 仓库形态 | 未提交改动 `main.cpp` 654 行、29 个未跟踪文件、无 `.gitattributes` | 任何重构都没有可回滚的基线 |
| 生成物 | `src/glyph_data.cpp` 835 KB 入库，但生成它的输入**不在仓库** | 字体/符号数据事实上已经无法重建 |
| 自动化 | 33 个脚本平铺根目录，无 runner、无断言汇总、无 CI | 只能人工逐个跑，等于没有回归网 |

## 三、问题清单

### P0 —— 先止血，否则后面每条改动都不可回滚

#### P0-1 仓库处于"改了半年没提交"的状态

**现象**：`src/main.cpp` 有 654 行未提交改动，29 个未跟踪文件（诊断脚本、`tools/*.py`、探针 html），12 个已跟踪文件有改动；`git diff` 还持续输出 `LF will be replaced by CRLF` 警告。

**影响**：真正的架构重构动辄上百行，没有干净基线意味着"出错就回不去"，也是前面所有问题里最贵的一条。

**方案**：
1. 加 `.gitattributes` 一句话定死行尾，消掉所有 CRLF 噪音：
   ```
   * text=auto eol=lf
   *.bat text eol=crlf
   *.png binary
   ```
   然后 `git add --renormalize .` 单独提交一次（只动行尾，独立成 commit 便于 cherry-pick）。
2. 把现有改动拆成 3~5 个主题提交（行尾归一 / 诊断脚本归档 / 未完成的设置入口 / 其余功能改动），不要一个 "update" 提交糊过去。
3. 未跟踪文件里要进仓库的（`test_hide_outside.py`、`test_hook_passthrough.py`、`tools/uia_probe.ps1`、`tools/uia_diag.cpp`）与纯一次性的（`tools/caret_probe*.html`、`tools/quick_probe.py`、`hook_listen.py` 这种被别的脚本调用的除外）分开处理，见 P0-3。

**成本**：0.5 天。**收益**：立竿见影，后面所有工作都建立在可回滚的基线上。

#### P0-2 字形库数据不可复现

**现象**：`src/glyph_data.cpp`（835 KB，全仓最大文件）是生成物，生成器 `tools/gen_glyph_data.py` 的输入是"参考页面的 `data/symbols.js`、`data/emoji.js`"——**这两个文件不在仓库里**，脚本 docstring 里的示例路径是 `C:/.../id-xxx/data`（`tools/gen_glyph_data.py:10-11`）。`CMakeLists.txt` 里也没有生成步骤，直接 `add_executable(... src/glyph_data.cpp)`。

**影响**：换台机器、或一年后想加一个符号分类、或想按新 Unicode 版本更新 emoji，都做不了；只能读懂 835 KB 转义字符串手改。这是仓库里唯一一处**不可重建**的东西，也是最大的单点。

**方案（按推荐顺序）**：
1. **入库中间数据**：把两份上游 js 转成一个稳定的紧凑文本（`data/glyph_src.txt`，脚本里已有的行式格式就够，估 300~500 KB 纯文本，可 diff、可 review），入库。
2. **CMake 里加生成步骤**：`add_custom_command(OUTPUT ${CMAKE_BINARY_DIR}/gen/glyph_data.cpp COMMAND python tools/gen_glyph_data.py data ${CMAKE_BINARY_DIR}/gen ...)`，`src/glyph_data.cpp` 改为构建产物。这样 `main.cpp` 的包含路径改成 `glyph_data.h` 从 gen 目录取，`glyph_data.cpp` 从仓库删除（体积从 2/3 降到 0）。
3. 如果不想让生成变成构建依赖（需要 python），退化方案：保留入库的 `glyph_data.cpp`，但 ① 文件头加 `// GENERATED by tools/gen_glyph_data.py from data/glyph_src.txt —— 不要手改`；② 把中间数据也入库；③ 加一个 `--check` 模式，在 PR 前比对"重新生成的结果与入库的是否一致"。

**成本**：1 天。**收益**：一次性把最大的不可维护点变成可维护。

#### P0-3 一次性诊断脚本与工具混在 `tools/`

**现象**：`tools/patch_emojicache.py`（26 KB）、`patch_pump.py`、`patch_readme.py` 已是入库文件（`git ls-files` 可见），但它们的作用是"对源码做一次性字符串替换"的历史补丁器——现在跑一次会损坏 `main.cpp`。同目录还躺着 `caret_probe.html`、`caret_probe2/3.html`、`caret_big*.html`、`quick_probe.py`、`click_diag.py` 这类用完即弃的探针。

**影响**：`tools/` 语义被污染，新人（或未来的你）分不清"哪些是可以依赖的开发工具，哪些是历史化石"，误跑补丁脚本的后果是灾难性的。

**方案**：建 `tools/archive/`（或直接 `git rm`，历史里随时可取），只把**长期有用**的留下并补齐用途说明：`gen_glyph_data.py`、`bench_emoji.cpp`/`bench2.cpp`、`uia_probe.ps1`/`uia_diag.cpp`、`inspect_cache.py`。README 的"测试脚本"表同步拆成"工具"与"归档"两节。

**成本**：2 小时。

### P1 —— 架构性，现在做便宜，再拖一年会翻倍

#### P1-1 单翻译单元 5588 行：按"叶子优先"切分

**现象**：`main.cpp` 内部其实已经用 38 条 `// ====` 分节划清了职责（常量、数据、字形库、工具、D2D 后端、字体、emoji 光栅化、图片缩略图、剪贴板读/写、视图、布局、绘制、交互、窗口过程、插入符、显示隐藏、钩子、托盘、入口）。分节是对的，只是**没有落到编译单元边界**。

**影响**：① 任何编译错误都要在 5588 行范围里找；② 无法做"纯逻辑"单元测试（所有函数都隐式依赖 117 个全局）；③ 每次改一行都全量重编 250 KB；④ 无法给不同模块加不同的编译选项（例如给 UIA/COM 部分加 `-fno-exceptions` 的审查）。

**方案**：**不要一次全切**。按"叶子优先、依赖单向"分四批，每批都能编译+跑现有脚本：

```
第 1 批（无 UI 依赖的纯函数，最容易，风险最低）
  util.h/.cpp      ← 318-322 Lower、323 U8N、587 LowerU8、616 FileBase、698/711 Utf8Bytes/PathBytes
  format.h/.cpp    ← 667 RelTime、687 SizeText
  perf.h/.cpp      ← 278-316 PerfMs、PerfAppend、PerfInit
  diag.h/.cpp      ← 289/3482 Trace、295 WarmLog

第 2 批（数据层，需要收拢全局，见 P1-2）
  clip_model.h/.cpp  ← ClipItem(106)、g_items、视图索引 BuildView(2337)、MatchQuery/MatchFilter(2320-2335)
  glyph.h/.cpp       ← 384-615 全部字形库解析/搜索/最近记录 + glyph_data.h

第 3 批（渲染与输入）
  paint.h/.cpp     ← 718-1160 绘制后端/路径/图标 + 2686-3300 各 Paint*
  layout.h/.cpp    ← 2363-2685 Layout/ComputeLayout/抽屉
  emoji_atlas.h/.cpp ← 1167-1730 光栅化 worker + 磁盘缓存
  thumb.h/.cpp     ← 1732-1968 图片缩略图
  caret.h/.cpp     ← 4563-4857 插入符 + UIA 兜底
  hook.h/.cpp      ← 5172-5376 键盘/鼠标钩子

第 4 批（外壳）
  window.cpp       ← PanelProc/MainProc/显示隐藏（3962-5171）
  main.cpp         ← 只剩 wWinMain + 初始化顺序

依赖方向：main → window → {paint, layout, hook} → {clip_model, glyph, emoji_atlas, caret} → {util, format, perf, diag}
```

每切一个模块的判断标准：**切完立刻重编 + 跑 `test_noactivate.py` + `test_glyph_insert.py`**，通过才进下一个。

**成本**：每批 0.5~1.5 天，共约 3 天。**收益**：单次增量编译从"全量"降到秒级；模块边界一旦存在，后面所有重构才有立足点。

#### P1-2 117 个全局状态：先收拢"视图三元组"，不追求一次清零

**现象**：`g_items`（数据）、`g_view`（过滤+排序后的索引）、`g_sel`/`g_top`（选择与滚动）是三份耦合状态，不变式分散在三处维护：

- `BuildView()` 末尾夹紧 `g_sel`（`main.cpp:2352-2354`）
- `ClampScroll()`（`main.cpp:3852`）维护 `g_top` 与 `g_sel` 的关系
- `PanelKeyDown`（`main.cpp:3976-3981`）删除条目时手写 `g_sel = 0; g_top = 0;` 再 `BuildView(); ComputeLayout();`

任何新增入口（比如"清空历史""批量删除"）都要记得重复这一串，漏了就是"列表越界选择"或"高亮错位"。

**方案**：定义 `struct ViewModel`，把 `items/view/sel/top` 变成成员，只暴露语义化方法（`Refresh()`、`MoveSel(int)`、`Page(int)`、`Erase(int viewIdx)`），并把 `ClampScroll`/`BuildView` 里的夹紧逻辑收进 `Refresh()`。**第一步不做文件拆分**：先在 `main.cpp` 里用 `#define g_items vm_.items` 之类的过渡宏，或直接整体改名后全局替换（`g_items`→`vm_.items`），编译通过即等价重构，风险极低。

其余全局按"谁写谁负责"分级保留（`g_panel`/`g_hook`/`g_d2d` 这类单例句柄可以继续当全局），**不要**为了"消掉全局"去造 ServiceLocator/单例容器——那是把简单问题变复杂。

**成本**：1~1.5 天。**收益**：消灭这一类"忘记夹紧"的隐性 bug 源头。

#### P1-3 `PanelProc` 491 行：把命中测试抽成 `HitTest`

**现象**：`WM_LBUTTONUP` 里是 36 处 `PtIn(L.xxx, pt)` 的线性判定链（`main.cpp:4405-4520` 一带），优先级（模态弹层 → 右键菜单 → 标题栏按钮 → 页签 → chips → 行 → 收藏/删除小按钮 → 面板外）完全靠"语句顺序"表达。

**方案**：
1. 定义 `enum class Hit { None, Close, Gear, Pin, Tab0..3, Chip, Row, StarBtn, DelBtn, Title, EdgeL, ... }` 和 `Hit HitTest(POINT pt) const`（实现在 layout 段，手里已经有 `Layout L`）。
2. `WM_LBUTTONUP` 变成 `switch (HitTest(pt))`，每个 case 3~5 行。
3. 顺带把"模态/菜单打开时只接受哪些命中"做成 `HitTest` 的入参约束，而不是靠 491 行里的 `if (g_modalOpen) ...` 提前 return。

**成本**：0.5 天。**收益**：`PanelProc` 预计降到 200 行以内；加控件从"插一段"变成"加一个 case"，是后续所有 UI 迭代的长期红利。

#### P1-4 页面类型判断散落 17 处

**现象**：`g_page == PG_HISTORY || g_page == PG_FAV` 出现 17 次（`PanelKeyDown` 里 5 次、`PanelConsumesBareKey`、各 `Paint*`…）。emoji 页与 symbol 页则靠"传 page 参数"双路复用（`GlyphCat(page,idx)`、`GlyphItems(page)`），但绘制层又分成两个几乎平行的函数 `PaintEmoji`（3024）/`PaintSymbols`（3068）。

**方案**：
1. 立刻可做：`static bool IsListPage()` / `IsGlyphPage()`，17 处替换掉。
2. 中期：`PaintEmoji`/`PaintSymbols` 合成一个 `PaintGlyphPage(HDC, int page)`（差异只有名称列与字体，用参数化），合并后预计省 60~100 行。
3. `ClipItem.kind` 是裸 `int` 0/1/2（`MatchFilter` 里 `switch (g_filter)` 用字面量 0/1/2 比较，`main.cpp:2330-2332`）→ 改成 `enum class ClipKind { Text, File, Image }`，`-Wswitch` 会帮你抓漏。

**成本**：半天。**收益**：删掉一类复制粘贴型分支。

#### P1-5 测试资产没有组织，也没有自动化入口

**现象**：33 个 `test_*.py` 全部平铺在仓库根目录，每个脚本自带一份 `ctypes` 的 `INPUT`/`GUITHREADINFO`/`KEYBDINPUT` 结构体定义（`test_noactivate.py:17-33` 与 `test_fav.py`、`test_pinned_insert.py` 等重复），都手写"启动程序 / 找面板 hwnd / 注入按键 / 清理"流程；没有 runner、没有断言汇总、没有任何 CI。

**影响**：① 重复代码导致修一处结构体要改 20 个文件（这次 29 个未跟踪文件里就有一半是这么长出来的）；② 没人会一次跑完 33 个脚本，回归等于不存在；③ 因为要真实桌面、真实键盘注入、抢前台，这些脚本天然不能跑在 CI 上——所以**必须**把"可 CI 的纯逻辑测试"分出来。

**方案**：
1. `tests/wvclip.py`：抽公共层（ctypes 结构、`launch()`/`wait_panel()`/`key()`/`assert_panel_visible()`/`cleanup()`），33 个脚本瘦身到 30~80 行。
2. 目录结构 `tests/desktop/`（现在这些，`pytest -m desktop`）与 `tests/pure/`（无需桌面的纯逻辑）。
3. 生成 `pytest.ini`，给每个脚本加 `def test_xxx()` 包装（现在的脚本是 `main()` 里一串 `assert`，包成 test 函数几乎零成本），这样 `pytest -m desktop -k noactivate` 就能只跑一条。
4. C++ 侧不引第三方框架：加 `winvclip.exe --selftest`，跑 `BuildView` 语义、`RelTime`/`SizeText`、字形表解析、`PanelConsumesBareKey` 的真值表（这个是纯函数，最好测）。配合 P1-1 的模块拆分，这些函数才可能被单独测。

**成本**：1.5 天。**收益**：把"33 个能跑的手工脚本"变成"一条命令给出红绿"。

#### P1-6 视觉规格存在两份真源

**现象**：`index.html`（56 KB）是视觉稿，C++ 侧 `main.cpp:54-82` 是颜色/尺寸常量的**手抄副本**，注释里写着 `// --canvas #F4F2ED` 这样的对应关系，靠人肉保持同步。

**方案**（按性价比）：
1. 最低成本：在 `index.html` 头部与 `main.cpp` 常量区互加一句"改这里必须同步改 X"，并把对应表列进 README。
2. 推荐：把 `index.html` 从仓库降级为 `docs/design/clipboard-reliquary.html`（它已经没有运行时作用，只是视觉参考），C++ 常量成为唯一真源；再加一个 20 行的脚本从 `main.cpp` 常量抽出一段 CSS 变量写回 html，做到"改 C++ 自动同步稿"。
3. 不建议：从 html 生成 C++ 常量（自绘布局与 CSS 布局的结构差异太大，做不成 1:1 映射）。

**成本**：0.5 天。

## 五、明确不建议做的（避免过度设计）

- **不要重写成 Qt/QML/Web 前端**。整个项目的价值就在"原生、无依赖、钩子与 caret 的精确控制"，重写会丢掉全部已验证的坑经验。
- **不要上 GPU 渲染/合成层**。README 已有性能结论（瓶颈是软件光栅化本身，已经用磁盘缓存绕开），换渲染器是纯风险。
- **不要为"消掉全局"引入单例容器/服务定位器/事件总线**。单进程单实例桌面程序，117 个全局里真正需要收敛的只有视图三元组那一组，其余句柄型全局反而清晰。
- **不要给 C++ 引第三方测试/日志/JSON 框架**。现有零依赖是特性；`--selftest` + 手写断言足够覆盖纯逻辑。
  （唯一的例外是 vendored 的 SQLite：事务化、崩溃安全的页级存储自己写一遍只会更慢更危险，
  见 `third_party/`。它按「公共领域单文件、不当作本项目代码维护」管理。）
- **不要一次把 5588 行拆成 15 个文件**。一次性大迁移会让 `git blame` 和全部 33 个回归脚本同时失去参照，分批才有"每步可验证"。
